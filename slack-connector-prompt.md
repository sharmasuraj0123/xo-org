# Prompt: Build a Slack Connector

Build a Slack connector in my project that lets users connect their Slack workspace so my app can read channels, search messages, post messages, and interact with threads on their behalf. This connector should also support a bot mode where users can tag the bot in any Slack thread and it responds contextually. Use a custom Slack App with OAuth 2.0 v2 and the Events API. This is the same approach Manus AI uses for their Slack integration.

The user flow should work like this: the user clicks a "Connect Slack" button in my app, gets redirected to Slack's OAuth consent page at `https://slack.com/oauth/v2/authorize` with the client ID and requested bot scopes, the user selects which workspace to install the app on and approves the permissions, Slack redirects back to my app's callback URL with a temporary authorization code, my app exchanges that code for a bot access token by calling `https://slack.com/api/oauth.v2.access` with the client ID, client secret, and code, and then stores the bot token encrypted in the database. Unlike Gmail and GitHub, Slack bot tokens do not expire — they remain valid indefinitely until the user uninstalls the app or a workspace admin revokes access, so there is no refresh token flow needed.

Before writing any code, the Slack App must be created at https://api.slack.com/apps. Click "Create New App", choose "From scratch", give it a name and pick a development workspace. Once created, go to "OAuth & Permissions" in the left sidebar and add a Redirect URL pointing to your callback endpoint, for example `https://yourapp.com/api/slack/callback`. Then scroll down to "Scopes" and add the bot token scopes. The scopes you need are: `channels:read` to list public channels, `channels:history` to read messages in public channels the bot is in, `groups:read` to list private channels the bot is in, `groups:history` to read messages in private channels, `chat:write` to send messages as the bot, `users:read` to list workspace members, `users:read.email` to get user email addresses, `im:read` to list direct message channels, `im:history` to read direct messages, `mpim:read` to list group DM channels, `mpim:history` to read group DMs, `reactions:read` to view emoji reactions on messages, `reactions:write` to add emoji reactions, `files:read` to access files shared in channels, `files:write` to upload files, `app_mentions:read` to receive events when users tag the bot, and `channels:join` to let the bot join public channels on its own. If you also need to search messages across the workspace, add the user token scope `search:read` because search is only available with user tokens, not bot tokens. After adding scopes, go to "Basic Information" in the left sidebar and copy the Client ID, Client Secret, and Signing Secret — you will need all three as environment variables.

For the Events API, which powers the bot-in-threads functionality, go to "Event Subscriptions" in your Slack App settings and enable it. Set the Request URL to your events endpoint, for example `https://yourapp.com/api/slack/events`. Slack will send a verification challenge to this URL immediately — your endpoint must respond with the challenge value to confirm ownership. Then subscribe to bot events: `app_mention` so the bot receives a notification when someone tags it with @botname, `message.channels` to receive new messages in public channels the bot is in, and `message.im` to receive direct messages sent to the bot. Every event Slack sends to your endpoint is signed with your app's Signing Secret using HMAC-SHA256 — you must verify this signature on every incoming request to ensure it actually came from Slack and not an attacker.

Build these API routes for the connector management side: A connect endpoint at `GET /api/slack/connect` that constructs the Slack OAuth URL with the bot scopes, a randomly generated `state` parameter stored in the session for CSRF protection, and your redirect URI, then redirects the user to Slack. A callback endpoint at `GET /api/slack/callback` that receives the authorization code and state from Slack, verifies the state matches what was stored in the session, then exchanges the code for tokens by posting to `https://slack.com/api/oauth.v2.access` with the client ID, client secret, and code. The response will contain the bot access token under `access_token`, the team ID and team name under `team.id` and `team.name`, the bot user ID under `bot_user_id`, and optionally a user access token under `authed_user.access_token` if you requested user scopes. Store the bot token encrypted in the database along with the workspace info. A status endpoint at `GET /api/slack/status` that returns whether the current user has an active Slack connection, which workspace is connected, and the bot's status. A disconnect endpoint at `DELETE /api/slack/disconnect` that revokes the token by calling `https://slack.com/api/auth.revoke` with the bot token and then removes the stored credentials from the database.

Build these API routes for the actual Slack functionality: A channels list endpoint that calls `GET https://slack.com/api/conversations.list` with the bot token to list all channels the bot has access to, supporting type filters for public channels, private channels, DMs, and group DMs. A channel messages endpoint that calls `GET https://slack.com/api/conversations.history` with a channel ID to read the message history, supporting pagination with a cursor and a limit parameter. A thread replies endpoint that calls `GET https://slack.com/api/conversations.replies` with a channel ID and thread timestamp to read all replies in a specific thread. A send message endpoint that calls `POST https://slack.com/api/chat.postMessage` with the channel ID, text content, and optionally a `thread_ts` parameter to reply within a thread instead of posting a new message. Support Block Kit formatting for rich messages with sections, headers, buttons, and other interactive elements. A users list endpoint that calls `GET https://slack.com/api/users.list` to get all workspace members with their display names, email addresses, and status. A search endpoint — if you have a user token with `search:read` scope — that calls `GET https://slack.com/api/search.messages` with a query string supporting Slack's search syntax like `from:@username`, `in:#channel`, `has:link`, `before:2024-01-01`. A reactions endpoint that calls `POST https://slack.com/api/reactions.add` to add an emoji reaction to a message. A file upload endpoint that calls the new `POST https://slack.com/api/files.getUploadURLExternal` followed by uploading to the returned URL and then calling `POST https://slack.com/api/files.completeUploadExternal` to finalize and share the file in a channel. And a channel join endpoint that calls `POST https://slack.com/api/conversations.join` to let the bot join a public channel it hasn't been added to yet.

For the Events API handler, build an endpoint at `POST /api/slack/events` that handles three types of incoming payloads. First, the URL verification challenge: when Slack sends a payload with `type: "url_verification"`, respond immediately with the `challenge` value in the response body — this only happens once during setup. Second, event callbacks: when the payload has `type: "event_callback"`, extract the event from `event` field and route it based on `event.type`. For `app_mention` events, extract the channel, thread timestamp, user who mentioned the bot, and the message text, then trigger your agent to process the request and post a reply back to the same thread using `chat.postMessage` with the `thread_ts` parameter. For `message` events in DMs, do the same but without requiring an @mention. Third, always respond with HTTP 200 within 3 seconds — Slack will retry if it doesn't get an acknowledgment quickly, so acknowledge the event immediately and process it asynchronously in the background using a job queue or async task. If you don't respond fast enough, Slack will send the same event again up to 3 times, and you'll get duplicate processing. Include deduplication logic using the `event_id` field to prevent handling the same event twice.

For the database, store per user: the connected Slack workspace ID (team ID), workspace name, encrypted bot access token, bot user ID (so you can identify messages from your own bot and ignore them to prevent loops), optionally an encrypted user access token if you requested user scopes, the authed user ID (the person who installed the app), connection status (connected, disconnected, or revoked), and timestamps for when it was connected and last updated. If you plan to support multiple workspaces per user or multiple users per workspace, add a separate installations table keyed by team ID and user ID.

The environment variables needed are: `SLACK_CLIENT_ID` from the Basic Information page of your Slack App, `SLACK_CLIENT_SECRET` from the same page, `SLACK_SIGNING_SECRET` also from the same page which is used to verify incoming event payloads, `SLACK_BOT_TOKEN` for development if you want a hardcoded token for testing, and `ENCRYPTION_KEY` for encrypting stored tokens at rest.

For security, encrypt all stored tokens at rest in the database. Verify the `state` parameter on OAuth callback to prevent CSRF attacks. Verify the Slack signing secret on every incoming event and slash command request — compute the HMAC-SHA256 of the request timestamp and body using your signing secret and compare it to the `X-Slack-Signature` header. Reject requests where the timestamp is more than 5 minutes old to prevent replay attacks. Never expose tokens to the frontend. The bot should always confirm with the user before posting messages to channels, especially public ones, when triggered from your app's UI — the exception is when responding to @mentions in Slack threads, where the user explicitly requested a response. Filter out the bot's own messages in the events handler to prevent infinite loops where the bot responds to its own messages. Rate limits in Slack are tiered: most Web API methods are Tier 2 which allows roughly 20 requests per minute per workspace, some methods like `chat.postMessage` are Tier 3 with a higher limit, and some admin methods are Tier 1 at about 1 request per minute. Handle 429 responses by reading the `Retry-After` header and backing off for the specified number of seconds.

For the UI, build a connector settings section with: a "Connect Slack" button when not connected that shows the official "Add to Slack" button style, the connected state showing the workspace name, bot status, and connected date, a list of channels the bot is currently in with the option to have the bot join additional public channels, a "Disconnect" button that revokes the token and removes the app from the workspace, and optionally a toggle to enable or disable the @mention bot functionality if the user wants the connector for data access only without the interactive bot.

There is no verification process like Google's OAuth app verification for Slack. Your app can be installed on any workspace immediately via the OAuth flow. The only review process is if you want to list your app publicly in the Slack Marketplace, which requires submission and approval, but for direct installation via OAuth URL there is no gate. During development, your app starts as installable only on your development workspace. To allow installation on other workspaces, go to "Manage Distribution" in your Slack App settings and follow the checklist to enable distribution.
