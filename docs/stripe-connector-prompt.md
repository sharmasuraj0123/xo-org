# Prompt: Build a Stripe Connector

Build a Stripe connector in my project that lets users connect their Stripe account so my app can read customers, charges, invoices, subscriptions, payment links, and balances, and can perform actions like creating customers, issuing refunds, and generating payment links on their behalf. Use Stripe Connect OAuth 2.0 to let users connect their existing Stripe accounts to your platform without sharing their secret API keys. This is the same approach Manus AI uses for their Stripe connector.

The user flow should work like this: the user clicks a "Connect Stripe" button in my app, gets redirected to Stripe's authorization page at `https://connect.stripe.com/oauth/authorize` with your platform's client ID and the requested scope, the user either signs into their existing Stripe account or creates a new one, approves the connection, and Stripe redirects them back to your app's callback URL with a temporary authorization code. Your app exchanges that code for an access token and the connected account's Stripe account ID by posting to `https://connect.stripe.com/oauth/token` with your secret API key, the authorization code, and `grant_type=authorization_code`. The response contains the `stripe_user_id` which is the connected account's ID (starts with `acct_`), an access token, and a refresh token. Store the `stripe_user_id` and the tokens encrypted in your database. From that point on, you can make API calls on behalf of the connected account by passing the `Stripe-Account` header with their account ID in every request, authenticated with your own platform's secret key.

Before writing any code, set up Stripe Connect in your Stripe Dashboard. Go to Settings → Connect settings (or visit https://dashboard.stripe.com/settings/applications), enable OAuth for Standard accounts, and configure your redirect URI to point to your callback endpoint, for example `https://yourapp.com/api/stripe/callback`. Copy the Client ID shown on this page — it starts with `ca_` and is different from your regular API keys. You will also need your platform's secret API key (starts with `sk_test_` for test mode or `sk_live_` for live mode) from the API keys section of your dashboard. Stripe provides separate test and live mode client IDs and keys, so make sure you use test mode credentials during development.

For the OAuth scope, you have two options. Use `read_write` if your app needs to both read data and perform actions like creating charges, refunds, or payment links on behalf of the connected account. Use `read_only` if your app only needs to view data like customers, charges, and balances without making any changes. For a Manus-style connector that can both read data and take actions, use `read_write`. The scope is passed as a query parameter when redirecting the user to Stripe's authorization page.

Build these API routes for the connector management side: A connect endpoint at `GET /api/stripe/connect` that constructs the Stripe OAuth authorization URL with your client ID, `response_type=code`, the requested scope (`read_write` or `read_only`), a `state` parameter containing a random string stored in the session for CSRF protection, and your redirect URI, then redirects the user to `https://connect.stripe.com/oauth/authorize` with these parameters. A callback endpoint at `GET /api/stripe/callback` that receives the authorization code and state from Stripe, verifies the state matches what was stored in the session, then exchanges the code for credentials by posting to `https://connect.stripe.com/oauth/token` with your secret API key as the authentication, the code, and `grant_type=authorization_code`. The response contains `stripe_user_id` (the connected account's ID), `access_token`, `refresh_token`, `scope`, `livemode` (boolean indicating test or live mode), and `stripe_publishable_key`. Store the `stripe_user_id`, encrypted access token, encrypted refresh token, scope, and livemode flag in the database linked to the current user. A status endpoint at `GET /api/stripe/status` that returns whether the current user has an active Stripe connection, the connected account ID, whether it's in live or test mode, and the account's business name and email fetched from `GET https://api.stripe.com/v1/accounts/{stripe_user_id}`. A disconnect endpoint at `DELETE /api/stripe/disconnect` that revokes access by posting to `https://connect.stripe.com/oauth/deauthorize` with your client ID and the connected account's `stripe_user_id`, then removes the stored credentials from the database.

Build these API routes for the actual Stripe functionality, all making requests with the `Stripe-Account: {stripe_user_id}` header to act on behalf of the connected account: A customers endpoint that calls `GET https://api.stripe.com/v1/customers` to list all customers, with support for pagination using `starting_after` and `limit` parameters, and filtering by email. A single customer endpoint that calls `GET https://api.stripe.com/v1/customers/{id}` to retrieve a specific customer's details including their payment methods, subscriptions, and invoices. A create customer endpoint that calls `POST https://api.stripe.com/v1/customers` with name, email, and optional metadata. A charges endpoint that calls `GET https://api.stripe.com/v1/charges` to list recent charges with pagination and optional filtering by `created` date range and `customer` ID. A balance endpoint that calls `GET https://api.stripe.com/v1/balance` to get the connected account's current balance across all currencies. A balance transactions endpoint that calls `GET https://api.stripe.com/v1/balance_transactions` to list recent transactions with amounts, fees, and net amounts. An invoices endpoint that calls `GET https://api.stripe.com/v1/invoices` to list invoices with filtering by customer, status (draft, open, paid, void, uncollectible), and date range. A subscriptions endpoint that calls `GET https://api.stripe.com/v1/subscriptions` to list active subscriptions with their plan details, current period, and status. A create payment link endpoint that calls `POST https://api.stripe.com/v1/payment_links` with a price ID and quantity to generate a shareable checkout URL. A refund endpoint that calls `POST https://api.stripe.com/v1/refunds` with a charge ID or payment intent ID and an optional amount for partial refunds. A products endpoint that calls `GET https://api.stripe.com/v1/products` to list all products, and a prices endpoint that calls `GET https://api.stripe.com/v1/prices` to list all prices associated with products. And a payouts endpoint that calls `GET https://api.stripe.com/v1/payouts` to list recent payouts to the connected account's bank.

For token management, Stripe Connect OAuth tokens for Standard accounts (the type used when connecting existing Stripe accounts) do not expire by default when using the legacy Connect OAuth flow. The access token remains valid indefinitely until the user disconnects or you revoke it. However, if you are building a Stripe App using the newer Stripe Apps OAuth flow, access tokens expire after 1 hour and refresh tokens expire after 1 year. In that case, refresh the access token by posting to `https://connect.stripe.com/oauth/token` with `grant_type=refresh_token` and the refresh token. The response contains a new access token and a new refresh token — store both, as refresh tokens are rolled on every exchange. For the simpler Standard Connect OAuth approach, you primarily use the `stripe_user_id` with the `Stripe-Account` header and your own platform's API key to make requests, so token expiry is not a concern. If the user disconnects their account, Stripe sends an `account.deauthorized` webhook event — listen for this to mark the connection as disconnected in your database.

For webhooks, set up an endpoint at `POST /api/stripe/webhooks` to receive events from Stripe. Configure this in your Stripe Dashboard under Developers → Webhooks, and add your endpoint URL with the events you want to listen for. The critical events for a connector are: `account.deauthorized` which fires when a connected account disconnects from your platform, `charge.succeeded` and `charge.failed` for payment notifications, `invoice.paid` and `invoice.payment_failed` for subscription billing events, and `payout.paid` for payout notifications. Every webhook request from Stripe includes a `Stripe-Signature` header — verify this signature using your webhook signing secret and the `stripe.webhooks.constructEvent` method from the Stripe SDK to ensure the request is authentic. Never process a webhook without verifying the signature.

For the database, store per user: the connected Stripe account ID (`stripe_user_id`, starts with `acct_`), encrypted access token, encrypted refresh token, the scope granted (`read_write` or `read_only`), whether the connection is in live mode or test mode, the connected account's business name and email (fetched from the Accounts API after connection), connection status (connected, disconnected, or revoked), and timestamps for when it was connected and last updated.

The environment variables needed are: `STRIPE_SECRET_KEY` which is your platform's secret API key from the Stripe Dashboard, `STRIPE_CLIENT_ID` which is the Connect client ID starting with `ca_` from your Connect settings, `STRIPE_WEBHOOK_SECRET` which is the signing secret for your webhook endpoint from the Webhooks section of your dashboard, and `ENCRYPTION_KEY` for encrypting stored tokens at rest.

Security is absolutely critical with Stripe because you are dealing with real money and sensitive financial data. Encrypt all stored tokens and account IDs at rest in the database. Never expose any Stripe keys or tokens to the frontend — all Stripe API calls must happen server-side only. Use the `state` parameter in the OAuth flow to prevent CSRF attacks. Verify webhook signatures on every incoming webhook request. Always confirm with the user before performing any write operation — the agent should explicitly ask before creating charges, issuing refunds, creating payment links, or modifying customer data. Default to test mode during development and make it visually obvious in your UI when a connection is in live mode versus test mode. Implement audit logging for every write operation (refunds, customer creation, payment link creation) with the user ID, action taken, amount, and timestamp. Rate limits on Stripe are generous — 100 read requests per second and 25 write requests per second in live mode, higher in test mode — but handle 429 responses with exponential backoff. Never log full card numbers or sensitive payment data. Use Stripe's idempotency keys for write operations to prevent duplicate charges or refunds if a request is retried.

For the UI, build a connector settings section with: a "Connect with Stripe" button using Stripe's official Connect button style when not connected, the connected state showing the business name, connected email, account ID, live/test mode indicator, and connected date, a permission summary showing whether the app has read-only or read-write access, a "Disconnect" button that revokes the connection and clears stored credentials, and a clear visual indicator distinguishing test mode connections from live mode connections so users never accidentally perform live transactions while testing.

There is no verification or review process required for using Stripe Connect OAuth with Standard accounts — any Stripe user can connect their account to your platform immediately. The only review process is if you want to list your integration as a Stripe App in the Stripe App Marketplace, which requires submission and approval, but for direct OAuth connections there is no gate.
