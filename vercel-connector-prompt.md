# Prompt: Build a Vercel Connector

Build a Vercel connector in my project that lets users connect their Vercel account so my app can list projects, trigger deployments, manage environment variables, check deployment status, manage domains, and roll back deployments on their behalf. Use a Vercel Integration with OAuth 2.0 to let users connect their existing Vercel accounts to your platform. Vercel calls their OAuth applications "Integrations" and the auth flow follows the standard OAuth 2.0 authorization code pattern.

The user flow should work like this: the user clicks a "Connect Vercel" button in my app, gets redirected to Vercel at `https://vercel.com/integrations/{your_integration_slug}/new` with a state parameter for CSRF protection, the user logs into their Vercel account if not already logged in, selects which projects or the full account to grant access to, approves the permissions, and Vercel redirects them back to your app's callback URL with a temporary authorization code and the state parameter. This code is short-lived and valid for only 30 minutes. Your app exchanges that code for a long-lived access token by posting to `https://api.vercel.com/v2/oauth/access_token` with the client ID, client secret, code, and redirect URI in `application/x-www-form-urlencoded` format. The response contains the access token, the `team_id` (which is null if installed on a personal account), and the `installation_id`. Store the access token encrypted in your database. If the response includes a `team_id`, you must append `?teamId={team_id}` to every subsequent API request to access that team's resources. Vercel access tokens obtained through the Integration flow are long-lived and do not expire, so there is no refresh token flow needed.

Before writing any code, create a Vercel Integration in the Integration Console. Go to your Vercel dashboard, navigate to Settings → Integrations → Integration Console (or visit https://vercel.com/dashboard/integrations/console), and click "Create Integration". Fill in the name, description, and logo for your integration. Set the Redirect URL to your callback endpoint, for example `https://yourapp.com/api/vercel/callback`. Under API Scopes, select the permissions your integration needs. The available scopes are granular and cover: read and write access to deployments, read and write access to projects, read and write access to project environment variables, read and write access to global account environment variables, read access to teams, read access to user information, read and write access to domains and certificates, read and write access to Edge Configs, read and write access to log drains, and read access to billing. Select only the scopes your connector actually needs — requesting fewer scopes makes users more comfortable granting access. For a full-featured connector that can deploy, manage projects, and handle environment variables, you would need: deployments (read/write), projects (read/write), project environment variables (read/write), domains (read/write), teams (read), and user (read). After creating the integration, copy the Client ID and Client Secret from the integration settings page.

Build these API routes for the connector management side: A connect endpoint at `GET /api/vercel/connect` that constructs the Vercel integration install URL at `https://vercel.com/integrations/{your_integration_slug}/new` with a `state` parameter containing a random string stored in the session for CSRF protection, then redirects the user to Vercel. A callback endpoint at `GET /api/vercel/callback` that receives the authorization code and state from Vercel, verifies the state matches what was stored in the session, then exchanges the code for an access token by posting to `https://api.vercel.com/v2/oauth/access_token` with `client_id`, `client_secret`, `code`, and `redirect_uri` as form-encoded body parameters. Store the access token, team ID, and installation ID encrypted in the database linked to the current user. After storing the token, fetch the user's profile by calling `GET https://api.vercel.com/v2/user` with the token in the Authorization header to get their username and email. A status endpoint at `GET /api/vercel/status` that returns whether the current user has an active Vercel connection, which account or team is connected, and the installation ID. A disconnect endpoint at `DELETE /api/vercel/disconnect` that removes the stored credentials from the database. Vercel does not have a token revocation API endpoint — the user would need to uninstall the integration from their Vercel dashboard to fully revoke access. Your disconnect endpoint should delete the stored token and mark the connection as disconnected on your side.

Build these API routes for the actual Vercel functionality, all making requests to `https://api.vercel.com` with the `Authorization: Bearer {access_token}` header and appending `?teamId={team_id}` if the connection is to a team: A projects list endpoint that calls `GET https://api.vercel.com/v9/projects` to list all projects in the account or team, returning project name, ID, framework, latest deployment URL, Git repository link, and created date. A single project endpoint that calls `GET https://api.vercel.com/v9/projects/{project_id_or_name}` to get detailed info about a specific project including its environment variables, domains, and deployment settings. A deployments list endpoint that calls `GET https://api.vercel.com/v6/deployments` to list recent deployments across all projects or filtered by project with the `projectId` query parameter, returning deployment URL, status (READY, ERROR, BUILDING, QUEUED, CANCELED), creation date, Git commit message, and branch. A single deployment endpoint that calls `GET https://api.vercel.com/v13/deployments/{deployment_id}` to get detailed status, build logs URL, and deployment metadata. A create deployment endpoint that calls `POST https://api.vercel.com/v13/deployments` with the project name, Git source (repository, branch, commit), and optional environment variable overrides to trigger a new deployment. A cancel deployment endpoint that calls `PATCH https://api.vercel.com/v12/deployments/{deployment_id}/cancel` to cancel a deployment that is currently building or queued. An environment variables endpoint that calls `GET https://api.vercel.com/v10/projects/{project_id}/env` to list all environment variables for a project with their keys, targets (production, preview, development), and whether they are encrypted. A create environment variable endpoint that calls `POST https://api.vercel.com/v10/projects/{project_id}/env` with key, value, target environments, and type (plain, encrypted, secret, system). A delete environment variable endpoint that calls `DELETE https://api.vercel.com/v10/projects/{project_id}/env/{env_id}` to remove an environment variable. A domains list endpoint that calls `GET https://api.vercel.com/v9/projects/{project_id}/domains` to list all custom domains attached to a project. An add domain endpoint that calls `POST https://api.vercel.com/v10/projects/{project_id}/domains` with the domain name to attach a custom domain to a project. A remove domain endpoint that calls `DELETE https://api.vercel.com/v9/projects/{project_id}/domains/{domain}` to detach a domain from a project. And a promote deployment endpoint that calls `POST https://api.vercel.com/v10/projects/{project_id}/promote/{deployment_id}` to promote a specific deployment to production, which is effectively how you do rollbacks — promote a previous deployment.

For webhooks, Vercel can send events to your integration when things happen on the connected account. Configure your webhook endpoint URL in the Integration Console settings. Vercel signs webhook payloads using your Integration Secret (Client Secret) — verify the signature on every incoming request. The key events to listen for are: `deployment.created` when a new deployment starts, `deployment.ready` when a deployment finishes successfully, `deployment.error` when a deployment fails, `deployment.canceled` when a deployment is canceled, `project.created` and `project.removed` for project lifecycle events, and `integration-configuration.removed` when the user uninstalls your integration. When you receive the `integration-configuration.removed` event, mark the connection as disconnected in your database and stop making API calls for that user.

For the database, store per user: the Vercel access token (encrypted), the team ID (null for personal accounts), the installation ID, the configuration ID, the connected Vercel username and email, connection status (connected, disconnected, or uninstalled), and timestamps for when it was connected and last updated. If you need to support users connecting both a personal account and a team account, store them as separate connections.

The environment variables needed are: `VERCEL_CLIENT_ID` which is the Client ID from your Integration Console, `VERCEL_CLIENT_SECRET` which is the Client Secret from the same page used for both the OAuth exchange and webhook signature verification, `VERCEL_INTEGRATION_SLUG` which is the URL slug of your integration used to construct the install URL, and `ENCRYPTION_KEY` for encrypting stored tokens at rest.

Security is important because the Vercel connector has the power to deploy code, modify environment variables that may contain secrets, and manage production domains. Encrypt the access token at rest in the database. Never expose the token to the frontend — all Vercel API calls must happen server-side. Use the state parameter in the OAuth flow to prevent CSRF attacks. Verify webhook signatures using your Client Secret on every incoming webhook. Require explicit user confirmation before triggering deployments, deleting projects, modifying environment variables, or changing domain configurations — these are high-impact actions. When displaying environment variable values, mask or hide the actual values since they often contain API keys and secrets — only show the key names and which environments they target. Log all write operations (deployments triggered, environment variables modified, domains changed) for audit purposes. Vercel rate limits API calls but does not publish exact numbers — handle 429 responses with exponential backoff using the Retry-After header.

For the UI, build a connector settings section with: a "Connect Vercel" button when not connected, the connected state showing the Vercel username, team name if applicable, and connected date, a list of projects the integration has access to, a "Disconnect" button that clears stored credentials, and optionally a quick-action panel showing recent deployments with their status so the user can see at a glance what's happening.

There is no separate verification or review process required for creating a Vercel Integration and using it with OAuth. Any Vercel user can install your integration immediately via the OAuth flow. The only review process is if you want to publish your integration publicly on the Vercel Marketplace, which requires submission and approval. For private or unlisted integrations distributed via direct install URL, there is no gate.
